1. Présentation

Vault-Tec Media Optimizer est une extension MediaWiki qui réduit le poids des médias d'un wiki de deux manières complémentaires : elle optimise les fichiers d'origine (PNG, JPEG, GIF) de façon sans perte, et elle génère pour chaque image une version WebP (et, en option, AVIF) servie automatiquement aux navigateurs via une balise <picture>. Les visiteurs reçoivent des images nettement plus légères sans perte de qualité visible, ce qui accélère le chargement et réduit la bande passante.

Les nouveaux fichiers téléversés sont traités automatiquement ; un mécanisme de rattrapage (« backfill ») traite l'intégralité des fichiers déjà présents. Trois pages spéciales offrent diagnostic, pilotage du rattrapage et statistiques détaillées.

1.1 Principe de fonctionnement

  • L'original optimisé : le fichier source est recompressé sans perte. Les pixels restent identiques ; seule la taille sur le disque diminue. Ce gain concerne l'espace de stockage serveur.
  • La version WebP : une copie WebP est générée et stockée séparément. C'est elle, beaucoup plus légère, qui est envoyée aux navigateurs compatibles. Ce gain concerne la bande passante et la vitesse pour les visiteurs.

La balise <picture> laisse le navigateur choisir : WebP (ou AVIF) s'il le supporte, format d'origine sinon. L'image originale reste toujours accessible (compatibilité totale, visionneuse multimédia, etc.).

1.2 Ce que l'extension ne fait pas

  • Elle n'altère jamais la qualité visuelle des originaux (sans perte pour les PNG ; ré-encodage haute qualité pour les JPEG).
  • Elle ne supprime pas les fichiers originaux : ils restent en place et accessibles.
  • Pour les GIF, l'optimisation de l'original est désormais possible et sans perte via gifsicle (§4.6) — strictement sûre pour l'animation, et désactivée par défaut. Sans gifsicle, seul le WebP du GIF est produit (comportement historique).
  • Elle ne dépend d'aucun service externe ou cloud : tout le traitement se fait sur votre serveur.

2. Prérequis & dépendances

La page spéciale VaultTec_État (§6.1) vérifie automatiquement l'ensemble de ces prérequis et signale tout problème.

2.1 Versions minimales

ComposantVersion requise
MediaWiki1.43 ou supérieur
PHP8.1 ou supérieur
Bibliothèque d'imagesImagick (recommandé) ou GD, avec support WebP

2.2 Bibliothèque de traitement d'image

L'extension utilise en priorité Imagick (plus fidèle et complète). En son absence, elle bascule sur GD. Dans les deux cas, le support WebP doit être actif, sans quoi la génération WebP est impossible.

Conseil. Imagick est fortement recommandé : meilleure gestion de la transparence PNG, des profils colorimétriques, et vrai WebP sans perte. La page VaultTec_État indique la bibliothèque active et son support WebP. Voir aussi le moteur libvips (§4.7), alternative rapide à grande échelle.

2.3 Système de fichiers

L'extension lit et écrit directement sur le système de fichiers local (backend FSFileBackend). Elle détecte les backends non locaux (S3, Swift) et le signale, car le traitement en place n'y est pas possible sans adaptation. Le répertoire WebP (images_webp/ par défaut) doit être accessible en écriture par l'utilisateur PHP.

2.4 Mémoire et temps d'exécution PHP

  • memory_limit : 256 Mo minimum (128 Mo suffit pour la plupart des images, mais peut échouer sur les très grandes). Le moteur libvips réduit nettement ce besoin (§16).
  • max_execution_time : peu critique, le gros du travail passant par la file de tâches asynchrone.

3. Installation

3.1 Mise en place des fichiers

Décompressez l'archive dans extensions/. Le dossier doit s'appeler exactement VaultTecMediaOptimizer :

extensions/VaultTecMediaOptimizer/
Important — transfert FTP. Transférez impérativement en mode binaire. Un transfert ASCII corrompt extension.json (fins de ligne/encodage) et provoque l'erreur « is not a valid JSON file » au démarrage. En cas de doute, décompressez directement sur le serveur via SSH.

3.2 Activation dans LocalSettings.php

wfLoadExtension( 'VaultTecMediaOptimizer' );

Les réglages personnalisés (§4) doivent être placés après cette ligne.

3.3 Mise à jour de la base de données

L'extension crée deux tables (vtmo_image_optimization, vtmo_zopfli_thumb_stats) et, en montée de version, ajoute une colonne. Lancez :

php maintenance/run.php update --quick

Sur MediaWiki < 1.40 : php maintenance/update.php --quick.

Note. Le script de mise à jour est idempotent : relançable sans risque.

3.3.1 En cas de blocage par une autre extension

Si update.php échoue à cause d'une autre extension (SQL non idempotent), soit (1) désactivez temporairement l'extension fautive, relancez, réactivez ; soit (2) créez les objets manuellement :

ALTER TABLE vtmo_image_optimization
  ADD COLUMN IF NOT EXISTS io_png_zopfli_size INT UNSIGNED DEFAULT NULL;

CREATE TABLE IF NOT EXISTS vtmo_zopfli_thumb_stats (
  zts_id INT UNSIGNED NOT NULL,
  zts_thumb_count INT UNSIGNED DEFAULT 0 NOT NULL,
  zts_bytes_saved BIGINT UNSIGNED DEFAULT 0 NOT NULL,
  zts_updated_at BINARY(14) DEFAULT NULL,
  PRIMARY KEY(zts_id)
);

3.4 Vérification post-installation

Rendez-vous sur Spécial:VaultTec_État. Tous les contrôles doivent être au vert (ou orange pour les éléments optionnels non bloquants) avant de lancer le rattrapage.

4.6 Optimisation GIF (gifsicle) NOUVEAU

Première passe GIF strictement sans perte et sûre pour l'animation, via le binaire externe gifsicle. Seul -O{niveau} est passé (jamais resize/lossy/colors) : dimensions, frames, cadence et boucle sont préservées — le rendu est identique au pixel près. Tourne à l'upload et dans le rattrapage CLI ; gifsicle absent ou désactivé = no-op inoffensif (le WebP est tout de même généré).

ParamètreDéfautDescription

…GifsicleBinarygifsicleChemin ou nom de commande du binaire.
…GifsicleLevel3Niveau -O (1–3). 3 essaie le plus de stratégies.

4.7 Moteur libvips (optionnel) NOUVEAU

Moteur d'image alternatif basé sur le binaire vips (aucune extension PHP requise). Même qualité WebP qu'Imagick/GD (même bibliothèque libwebp), mais beaucoup plus rapide et léger en mémoire à grande échelle (voir §16). Repli automatique sur Imagick/GD si le binaire est inutilisable.

ParamètreDéfautDescription
…ImageEngineautoauto (Imagick puis GD) ou vips.
…VipsBinaryvipsChemin ou nom de commande du binaire vips.

4.8 Mode « gros wiki » : file de tâches NOUVEAU

ParamètreDéfautDescription
…UseJobQueuetruefalse = ne plus enfiler à l'upload : on optimise les originaux en CLI (§8.6) à son rythme. Les miniatures reçoivent quand même leur WebP à la demande au rendu.

4.9 AVIF (expérimental) EXPÉRIMENTAL

Génère une copie AVIF en plus du WebP et la propose avant le WebP dans <picture> (les navigateurs compatibles choisissent l'AVIF, les autres retombent sur WebP puis l'original). Selon le contenu et l'encodeur, l'AVIF peut être plus compact que le WebP à qualité égale (surtout sur des photos lisses) — mais ce n'est pas systématique (sur du bruit ou en haute qualité il peut être plus gros), il encode bien plus lentement, et exige un encodeur AV1 (Imagick+libheif/AV1, PHP-GD imageavif(), ou libvips heifsave+AV1). L'extension sonde réellement la capacité AV1 et retombe proprement sur le WebP si elle manque.

ParamètreDéfautDescription
…AvifEnabledfalseActive la génération AVIF (en plus du WebP).
…AvifDirectoryimages_avifRépertoire des copies AVIF (sibling de images/).
…AvifQuality50Qualité AVIF (0-100). ≈ 45-55 ≈ WebP 80-85 visuellement (le gain réel dépend du contenu et de l'encodeur).

5. Architecture technique

5.1 Flux de traitement d'un fichier

  1. Vérification : type MIME autorisé ? taille sous la limite ? fichier accessible en écriture ?
  2. Optimisation de l'original (si activée) : recompression sans perte (PNG/JPEG ; GIF via gifsicle, §4.6). Garde-fou : le résultat n'écrase l'original que s'il est strictement plus petit.
  3. Métadonnées 1.8.1 : si la 1ʳᵉ passe a réduit l'original, les métadonnées MediaWiki (img_sha1, img_size) sont resynchronisées (sinon détection de doublons et invalidation du cache des miniatures restaient faussées).
  4. Génération WebP (et AVIF si activé) dans le répertoire dédié.
  5. Enregistrement : tailles originale/optimisée/WebP consignées en base pour les statistiques.
Garde-fou anti-gonflage. L'optimisation écrit toujours dans un fichier temporaire et ne remplace l'original que si la nouvelle version est strictement plus petite : une optimisation ne peut jamais augmenter la taille d'un fichier. Les écritures sont atomiques (temp unique + rename).

5.2 Diffusion via la balise picture

À l'affichage (action view), un hook enveloppe les <img> dans une <picture> proposant la source WebP (et AVIF avant elle si activé), avec repli sur l'original. Le HiDPI (Retina) est géré via srcset (1x, 1,5x, 2x).

Point important. Une source n'est émise que si le fichier WebP/AVIF existe réellement sur le disque : contrairement à <img srcset>, une source manquante dans <picture> ne se replie pas et afficherait une image cassée. Corollaire (correctif 1.8.1) : sous GD, un GIF animé ne reçoit pas de WebP/AVIF (GD ne décode que la 1ʳᵉ frame) — le GIF animé d'origine est conservé pour ne jamais figer l'animation. Imagick/libvips produisent un WebP/AVIF animé et ne sont pas concernés.

5.3 Génération des WebP : à la création et à la demande

  • À la création : à la génération d'une miniature par MediaWiki, un hook produit immédiatement son WebP.
  • À la demande : au rendu d'une page, si une miniature utilisée n'a pas encore de WebP mais que sa source existe sur disque, le WebP manquant est généré à cet instant (borné par OnDemandThumbLimit).

Ce double mécanisme garantit qu'aucune taille réellement utilisée ne reste sans WebP, y compris les miniatures créées avant l'installation. Le premier rendu d'une page « froide » peut être légèrement plus lent ; les suivants sont instantanés (WebP en cache disque).

5.4 Traitement asynchrone

Le rattrapage passe par la file de tâches (JobQueue), pas par les requêtes web. Deux types de tâches : optimisation d'image standard et recompression zopflipng/oxipng. En mode gros wiki (§4.8), on shunte la file au profit du CLI (§8.6).

5.5 Stockage et cache

Suivi dans vtmo_image_optimization (une ligne par fichier). Statistiques agrégées en cache (WANObjectCache, courte durée), invalidé à chaque écriture. Statistiques portables sur MySQL/MariaDB, SQLite et PostgreSQL.

6.1 VaultTec_État (diagnostic)

Vérifie tout l'environnement avec un code couleur (vert/orange/rouge) : PHP, MediaWiki, mémoire, bibliothèques d'images et support WebP, moteur actif (Imagick/GD/vips) et sa sonde, système de fichiers et répertoires, table de base, état du second passage PNG (moteur, exécution shell, binaire), disponibilité de gifsicle et de l'AVIF/AV1, compatibilité, configuration. Premier endroit à consulter en cas d'anomalie.

6.2 VaultTec_Optimisation (rattrapage)

Pilote le traitement des fichiers existants : nombre de fichiers restants, programmation de lots dans la file. Si le second passage PNG est disponible, un bouton lance la recompression zopflipng/oxipng des existants.

6.3 VaultTec_Statistiques

Vue d'ensemble des gains, calculés à partir des tailles réellement mesurées (avant/après chaque étape).

6.3.1 Les trois mesures de gain

  • Espace total économisé : de l'état initial au fichier réel actuel (chiffre le plus représentatif).
  • 1ᵉʳ passage : gain de l'optimisation à l'upload.
  • 2ⁿᵈ passage : gain supplémentaire d'oxipng/zopflipng (si présent).
Gain faible si déjà optimisé. La taille « de départ » est celle au premier traitement par l'extension, pas la photo brute. Si vos fichiers étaient déjà propres, il reste peu à gagner — ce n'est pas une contre-performance.

6.3.2 Bilan de l'espace disque

Additionne l'espace gagné sur les originaux et soustrait l'espace des WebP générés (un par image, en plus de l'original). Le bilan net est presque toujours négatif : les WebP pèsent plus que ce qui est gratté.

Le WebP coûte du disque, mais économise de la bande passante. C'est normal et attendu : le WebP vise la bande passante (le vrai bénéfice), pas le stockage. Voir §16 pour le chiffrage honnête.

6.3.3 Bande passante économisée par page (estimation)

Illustre l'économie sur une page-type (miniatures, pas originaux). Estimation, pas mesure : le pourcentage de réduction est fiable (tailles réelles) ; le volume absolu dépend du trafic et des caches navigateur/CDN qui réduisent fortement le trafic effectif. Ordre de grandeur, pas une facture (cf. §16).

6.3.4 Autres sections

Taux de compression (originaux sans perte et WebP), répartition par format, section second passage PNG, répartition par moteur, et liste des fichiers en échec.

7. Installation des binaires de second passage

7.1 Le piège open_basedir

Beaucoup d'hébergements (Plesk…) restreignent les chemins lisibles/exécutables par PHP via open_basedir : un binaire dans /usr/bin/ fonctionne en ligne de commande mais reste invisible côté web.

Règle d'or. Placez toujours le binaire dans l'arborescence du wiki (ex. bin/) et configurez son chemin absolu complet, jamais un simple nom de commande.

7.2 Installation d'oxipng (recommandé)

Les binaires génériques peuvent exiger une glibc plus récente (« GLIBC_2.34 not found »). Le plus fiable est de compiler sur la machine (via cargo), puis de copier le binaire dans l'arborescence du wiki :

mkdir -p /chemin/vers/wiki/httpdocs/bin
cp /source/oxipng /chemin/vers/wiki/httpdocs/bin/oxipng
chmod 755 /chemin/vers/wiki/httpdocs/bin/oxipng
chown utilisateur:groupe /chemin/vers/wiki/httpdocs/bin/oxipng
/chemin/vers/wiki/httpdocs/bin/oxipng --version
$wgVaultTecMediaOptimizerZopfliEnabled = true;
$wgVaultTecMediaOptimizerPngEngine = 'oxipng';
$wgVaultTecMediaOptimizerOxipngBinary = '/chemin/vers/wiki/httpdocs/bin/oxipng';

7.3 Vérifier l'exécution shell côté web

L'extension a besoin de proc_open/exec. Si elles sont dans disable_functions, le second passage (et gifsicle/vips) est impossible. La page VaultTec_État indique l'état de l'exécution shell dans le contexte web (qui peut différer de la CLI).

8. Maintenance

8.1 Lancer le rattrapage initial

Lancez le rattrapage depuis Spécial:VaultTec_Optimisation (planifie des lots dans la file).

Préférez la ligne de commande pour les gros volumes. La page spéciale ne traite pas directement : elle enfile des tâches. Par défaut MediaWiki les exécute en fin de requête visiteur ($wgJobRunRate) — ce sont alors vos visiteurs qui paient l'encodage et le wiki paraît lent. N'augmentez pas $wgJobRunRate : la bonne valeur pour un traitement lourd est 0, combinée à un runJobs.php en SSH (dans un screen), ou au backfill CLI dédié (§8.6).

screen -S vtmo-jobs
php maintenance/run.php runJobs.php --type VaultTecMediaOptimizerOptimizeImage

8.2 Réparer des originaux indûment gonflés

repairBloatedOriginals.php répare les fichiers dont la version « optimisée » serait plus grosse que l'original (défaut historique), recompresse avec le moteur PNG configuré, corrige les tailles en base et resynchronise les métadonnées. Toujours commencer par --dry-run :

php maintenance/run.php .../repairBloatedOriginals.php --dry-run
php maintenance/run.php .../repairBloatedOriginals.php --max=20   # valider le rythme
php maintenance/run.php .../repairBloatedOriginals.php            # tout (dans un screen)
Astuce — chemin du script. En cas de « Script not found », utilisez le chemin absolu du script et de run.php. Lancez toujours via maintenance/run.php.

8.3 Recompresser avec un second moteur (oxipng puis zopflipng)

Pour la meilleure compression PNG : d'abord oxipng (rapide) sur tout le stock, puis zopflipng (lent) en finition via recompressOriginals.php.

À comprendre. Le PNG étant sans perte, chaque moteur ré-encode depuis les pixels : enchaîner oxipng puis zopflipng ne cumule pas les gains — le résultat est celui du dernier moteur. L'intérêt de l'enchaînement est de dégonfler vite le gros du stock avec oxipng, puis de ne lancer le lent que pour la finition. Une protection ne garde la sortie que si elle est plus petite.
# 1er passage (moteur configuré, ex. oxipng)
/opt/plesk/php/8.4/bin/php /abs/wiki/maintenance/run.php \
  /abs/wiki/extensions/VaultTecMediaOptimizer/maintenance/recompressOriginals.php
# 2e passage : PngEngine = 'zopflipng' dans LocalSettings, puis :
... recompressOriginals.php --reset      # remet les PNG à « à faire »

--dry-run prévisualise, --max=N limite. Les miniatures ne sont pas reprises en masse : purgez-les pour forcer leur régénération avec le moteur courant.

8.4 Purge du cache après modification des messages

php maintenance/run.php rebuildLocalisationCache --force

8.5 En-têtes de cache HTTP (recommandation)

Configurez un Cache-Control long sur les .webp (et .avif) du répertoire images_webp/. Levier majeur et souvent négligé pour réduire la bande passante (voir §16).

8.6 Backfill en ligne de commande — optimizeImages.php NOUVEAU

Rattrapage direct en CLI des images existantes (1ʳᵉ passe + WebP) sans passer par la file — idéal gros wiki. Honore le moteur configuré (vips inclus).

// LocalSettings.php (mode gros wiki)
$wgVaultTecMediaOptimizerUseJobQueue = false;
screen -S vtmo
php maintenance/run.php .../optimizeImages.php --dry-run          # aperçu
php maintenance/run.php .../optimizeImages.php --batch=200         # par lots
php maintenance/run.php .../optimizeImages.php --format=gif        # un seul format
php maintenance/run.php .../optimizeImages.php --start=Foo.png --max=500 --force

Options : --dry-run, --batch, --max, --start, --force, --format (sous-ensemble des formats configurés), --purge-queue. Le script purgeQueue.php vide la file Optimisation (et, avec --include-zopfli, la file du second passage).

Une seule voie à la fois pour un même stock : soit la file (runJobs.php), soit le CLI (optimizeImages.php). Ne lancez pas les deux en même temps (écritures atomiques = pas de corruption, mais travail en double) ; utilisez --purge-queue au besoin.

9. Dépannage

9.1 « is not a valid JSON file » au démarrage

extension.json corrompu, souvent par un transfert FTP ASCII. Re-transférez en binaire ou décompressez sur le serveur.

9.2 Erreur de colonne inconnue sur les statistiques

Migration non appliquée : lancez update.php (§3.3), ou la migration manuelle (§3.3.1).

9.3 Binaire de recompression introuvable (alors qu'il existe)

Cause la plus fréquente : open_basedir (§7). Copiez le binaire dans le wiki et donnez le chemin absolu. Vérifiez aussi la bonne variable (…OxipngBinary pour oxipng) et la casse. « GLIBC not found » = recompilez le binaire.

9.4 La recompression est très lente

zopflipng est intrinsèquement lent : passez à oxipng, ou réduisez les itérations (ex. 5). Voir §16.

9.5 Statistiques incohérentes pendant un traitement

Normal : les valeurs évoluent jusqu'à la fin (« Progression » à 100 %). Le total WebP peut fluctuer le temps que la resynchronisation des métadonnées régénère certaines miniatures.

9.6 Une image reste servie en PNG/JPEG plutôt qu'en WebP

Rechargez la page une fois (le 1ᵉʳ rendu génère les WebP manquants), puis de nouveau. Vérifiez les droits d'écriture du répertoire WebP et OnDemandThumbLimit > 0. Pour un GIF animé sous GD, l'absence de WebP est voulue (§5.2) afin de ne pas figer l'animation.

9.7 Droits sur les fichiers

Lancez les scripts sous l'utilisateur PHP, jamais en root (sinon fichiers non réécrasables ensuite).

11. Foire aux questions

L'extension modifie-t-elle la qualité de mes images ?
Non pour les originaux (PNG sans perte ; WebP de PNG sans perte par défaut). Les JPEG sont ré-encodés à haute qualité (85), visuellement indistinguable. Ajustable via …WebPQuality.

Que voient les navigateurs sans WebP ?
L'image d'origine, intacte (repli <img>). Tous les navigateurs récents supportent le WebP.

Dois-je activer le second passage PNG ?
Non obligatoire : il n'apporte qu'un gain disque. Activez-le si le stockage est une préoccupation.

Les GIF animés sont-ils préservés ?
Oui. L'optimisation gifsicle (§4.6) est strictement sans perte et sûre pour l'animation ; et sous GD, les GIF animés ne reçoivent jamais de WebP/AVIF figé (§5.2).

Combien vais-je gagner ?
Côté visiteurs, le WebP réduit souvent de 25 à 50 % le poids des images servies (cf. §16, chiffrage honnête au niveau miniature). Le gain disque sur les originaux est plus modeste.

Stockage cloud (S3, Swift) ?
Conçu pour un système de fichiers local ; les backends non locaux sont détectés et signalés (non pris en charge en l'état).

13. Sécurité

13.1 Exécution de binaires externes

Les binaires (gifsicle, zopflipng, oxipng, vips) sont invoqués via proc_open/exec avec les arguments passés en tableau (pas de chaîne shell) → aucune interprétation par le shell, aucun risque d'injection. Les chemins viennent exclusivement de la configuration admin, jamais d'une entrée utilisateur.

13.2 Protection contre la traversée de répertoires

La génération WebP à la demande rejette tout nom contenant .., un séparateur (/ ou \) ou un octet nul. Les noms MediaWiki légitimes n'en contiennent jamais.

13.3 Restriction aux types autorisés

Traitement strictement limité aux types MIME configurés (PNG/JPEG/GIF par défaut) et plafonné par …MaxFileSize.

13.4 Droits d'accès

Les pages spéciales et actions sensibles sont réservées au droit vaulttecmediaoptimizer-admin.

13.5 Innocuité des balises générées

La réécriture enveloppe les <img> existants et ajoute une source WebP/AVIF ; les attributs d'origine sont préservés et les URL encodées. Aucune donnée arbitraire injectée.

16. Benchmarks — coût / bénéfice NOUVEAU

Deux familles de chiffres. (A) un modèle coût/bénéfice du wiki réel, recalculé depuis des hypothèses explicites ; (B) des mesures réelles (PHP 8.4, libvips 8.15.1, ImageMagick 6.9.12, gifsicle 1.94, zopflipng, PHP-GD ; un seul cœur). Reproductible via docs/benchmarks/model.py et tests/integration/pipeline.php.

Hypothèses du modèle (unités décimales ; 365 j/an) : originaux 52,62 Go PNG+JPEG ; trafic borne haute (cache froid) 100 000 vues/j × 10 miniatures ; miniature moyenne 55,3 Ko ; optimisation sans perte de miniature −13,7 % ; WebP de miniature −34 % (≈ −43 % vs brut) ; recompression des originaux −7/−16/−24 % (bas/médian/haut) ; copies WebP ≈ 70 % de l'original optimisé, stockées en plus.

Cadrage honnête. Les pages servent des miniatures (déjà petites), pas les originaux, et le WebP ajoute du disque. On sépare donc la bande passante servie (le vrai bénéfice) de la compression par fichier.

16.1 Bande passante servie

~55 → ~31 Go/jour (−43 %), ~8,7 To/an — borne haute (cache froid).

Le ratio −43 % est robuste ; le To/an absolu fond avec le cache navigateur/CDN.

16.2 Disque : le WebP en ajoute

Le disque monte (52,6 → ~75 Go au médian) : les WebP s'ajoutent aux originaux.

L'arbitrage : coût disque ponctuel (~+22 Go médian) vs économie de bande passante récurrente.

16.3 Compression par fichier (mesurée) — ≠ bande passante

Gains par fichier (pas le trafic) ; le moteur compte (GD ≈ 2,7× plus gros en lossless) ; AVIF : gain dépendant de la qualité et de l'encodeur (pas toujours plus petit — cf. §16.3).

16.4 GIF & 2ᵉ passe PNG (disque)

gifsicle −60 à −66 % (sans perte, ~20 ms) ; 2ᵉ passe zopflipng ~−12 % de disque mais lente (~14 s).

16.5 Moteur : mémoire, vitesse, débit

libvips ~1,8× moins de mémoire (grande image) et ~5× moins / ~40× plus vite (miniatures) ; débit ~245→~65 img/min selon la richesse média (la bande passante reste ~−71/−72 %).

What's new since v1.4.1 (through 1.8.1). This manual integrates everything added after the 1.4.1 documentation: optional libvips image engine (§4.7), lossless GIF optimization via gifsicle (§4.6), large-wiki CLI mode (§4.8 and §8.6), experimental AVIF (§4.9), dependency installation (§2.5), a cost/benefit benchmarks section (§16), and the 1.8.1 fixes (metadata refresh after the first pass; animated GIFs never frozen under GD). Experimental items (AVIF) are marked EXPERIMENTAL.

1. Overview

Vault-Tec Media Optimizer is a MediaWiki extension that reduces a wiki's media weight in two complementary ways: it optimizes the original files (PNG, JPEG, GIF) losslessly, and it generates a WebP version (and, optionally, AVIF) of each image, served automatically to browsers through a <picture> tag. Visitors receive substantially lighter images with no visible loss, which speeds up page loads and cuts bandwidth.

New uploads are processed automatically; a backfill mechanism processes every file already present. Three special pages provide diagnostics, backfill control and detailed statistics.

1.1 How it works

  • The optimized original: the source file is recompressed losslessly. Pixels stay identical; only on-disk size drops. This saving is about server storage.
  • The WebP version: a WebP copy is generated and stored separately. This much lighter version is sent to compatible browsers. This saving is about bandwidth and load speed for visitors.

The <picture> tag lets the browser choose: WebP (or AVIF) if supported, the original format otherwise. The original image always remains available (full compatibility, media viewer, etc.).

1.2 What the extension does not do

  • It never degrades the visual quality of originals (lossless for PNG; high-quality re-encode for JPEG).
  • It never deletes original files: they stay in place and accessible.
  • For GIF, optimizing the original is now possible and lossless via gifsicle (§4.6) — strictly animation-safe and off by default. Without gifsicle, only the GIF's WebP is produced (historical behaviour).
  • It depends on no external or cloud service: all processing happens on your server.

2. Prerequisites & dependencies

  • max_execution_time: not critical — the bulk of work goes through the async job queue.

5. Technical architecture

5.1 File processing flow

  1. Validation: allowed MIME? under size limit? writable?
  2. Original optimization (if enabled): lossless recompress (PNG/JPEG; GIF via gifsicle, §4.6). Guard: the result replaces the original only if strictly smaller.
  3. Metadata 1.8.1: if the first pass shrank the original, MediaWiki metadata (img_sha1, img_size) is refreshed (otherwise duplicate detection and thumbnail cache invalidation stay stale).
  4. WebP generation (and AVIF if enabled).
  5. Recording: original/optimized/WebP sizes stored for statistics.
Anti-bloat guard. Optimization always writes to a temp file and replaces the original only if strictly smaller — it can never increase a file's size. Writes are atomic (unique temp + rename).

5.2 Delivery via the picture tag

On render, a hook wraps <img> in <picture> offering the WebP source (and AVIF before it if enabled), with fallback to the original; HiDPI via srcset.

Important. A source is emitted only if the WebP/AVIF file actually exists on disk: unlike <img srcset>, a missing <picture> source does not fall back and would show a broken image. Corollary (1.8.1 fix): under GD, an animated GIF gets no WebP/AVIF (GD decodes only the first frame) — the animated GIF is kept so the animation is never frozen. Imagick/libvips produce animated WebP/AVIF and are unaffected.

5.3 WebP generation: on creation and on demand

  • On creation: when MediaWiki generates a thumbnail, a hook immediately produces its WebP.
  • On demand: at render, if a used thumbnail has no WebP yet but its source exists on disk, the missing WebP is generated then (bounded by OnDemandThumbLimit).

This covers every size actually used, including thumbnails created before install. A cold page's first render may be slightly slower; later renders are instant (WebP cached on disk).

5.4 Asynchronous processing

The backfill uses the JobQueue, not web requests (two job types: standard optimization and zopflipng/oxipng recompression). In large-wiki mode (§4.8), the queue is bypassed in favour of the CLI (§8.6).

5.5 Storage and cache

Tracking in vtmo_image_optimization; aggregate stats cached (WANObjectCache), invalidated on each write. Stats are portable across MySQL/MariaDB, SQLite and PostgreSQL.

7.2 Installing oxipng (recommended)

Generic binaries may need a newer glibc (“GLIBC_2.34 not found”); the safest path is to compile on the machine (cargo) then copy into the wiki tree:

mkdir -p /path/to/wiki/httpdocs/bin
cp /src/oxipng /path/to/wiki/httpdocs/bin/oxipng
chmod 755 /path/to/wiki/httpdocs/bin/oxipng
chown user:group /path/to/wiki/httpdocs/bin/oxipng

7.3 Verifying shell execution on the web side

The extension needs proc_open/exec. If they're in disable_functions, the second pass (and gifsicle/vips) is impossible. VTMOStatus reports shell execution in the web context.

8. Maintenance

8.1 Running the initial backfill

Launch from Special:VTMOBackfill (schedules batches).

Prefer the command line for large volumes. The special page only enqueues jobs; by default MediaWiki runs them at the end of visitor requests ($wgJobRunRate) — your visitors then pay for the encoding. Do not raise $wgJobRunRate: the right value for heavy work is 0, combined with runJobs.php over SSH (in a screen), or the dedicated CLI backfill (§8.6).
screen -S vtmo-jobs
php maintenance/run.php runJobs.php --type VaultTecMediaOptimizerOptimizeImage

8.2 Repairing improperly inflated originals

repairBloatedOriginals.php fixes files whose “optimized” version is larger than the original (legacy defect), recompresses with the configured engine, corrects DB sizes and refreshes metadata. Always start with --dry-run; use the absolute path if “Script not found”.

8.3 Recompressing with a second engine (oxipng then zopflipng)

Understand first. PNG is lossless, so each engine re-encodes from pixels: chaining oxipng then zopflipng does not add up — the result is the last engine's. The point is to deflate the bulk fast with oxipng, then run the slow one only for finishing. A guard keeps the output only if smaller.
... recompressOriginals.php            # first pass (configured engine)
# then set PngEngine = 'zopflipng' and:
... recompressOriginals.php --reset    # re-mark PNGs as to-do

8.4 Cache purge after message changes

php maintenance/run.php rebuildLocalisationCache --force

8.5 HTTP cache headers (recommendation)

Set a long Cache-Control on .webp (and .avif) under images_webp/ — a major, often-forgotten bandwidth lever (§16).

8.6 CLI backfill — optimizeImages.php NEW

Direct CLI backfill of existing images (first pass + WebP) without the queue — ideal for large wikis. Honours the configured engine (incl. vips).

// LocalSettings.php (large-wiki mode)
$wgVaultTecMediaOptimizerUseJobQueue = false;
screen -S vtmo
php maintenance/run.php .../optimizeImages.php --dry-run
php maintenance/run.php .../optimizeImages.php --batch=200
php maintenance/run.php .../optimizeImages.php --format=gif

Options: --dry-run, --batch, --max, --start, --force, --format, --purge-queue. purgeQueue.php empties the Optimize queue (and, with --include-zopfli, the second-pass queue). Use one path at a time per corpus (queue or CLI).

9. Troubleshooting

9.1 “is not a valid JSON file” at startup

Corrupt extension.json (usually ASCII FTP). Re-transfer in binary or unpack on the server.

9.2 Unknown-column error on statistics

Migration not applied: run update.php (§3.3) or the manual migration.

9.3 Recompression binary not found (though it exists)

Usually open_basedir (§7). Copy into the wiki tree and set the absolute path; check the right variable and case. “GLIBC not found” = recompile.

9.4 Recompression is very slow

zopflipng is intrinsically slow: switch to oxipng, or lower iterations (e.g. 5). See §16.

9.5 Statistics look inconsistent during processing

Normal: figures change until 100%. The WebP total may fluctuate while metadata refresh regenerates some thumbnails.

9.6 An image is served as PNG/JPEG instead of WebP

Reload once (the first render generates missing WebP), then again. Check WebP directory permissions and OnDemandThumbLimit > 0. For an animated GIF under GD, the missing WebP is intended (§5.2).

9.7 File permissions

Run scripts as the PHP user, never as root (otherwise unwritable files later).

11. Frequently asked questions

Does it change image quality?
Not for originals (lossless PNG; lossless WebP for PNG by default). JPEGs are re-encoded at high quality (85), visually indistinguishable. Tunable via …WebPQuality.

What do non-WebP browsers see?
The original image, intact (<img> fallback).

Must I enable the PNG second pass?
No — disk-only gain. Enable it if storage matters.

Are animated GIFs preserved?
Yes. gifsicle (§4.6) is strictly lossless and animation-safe, and under GD animated GIFs never get a frozen WebP/AVIF (§5.2).

How much will I save?
For visitors, WebP often cuts served-image weight by 25-50% (see §16, honest thumbnail-level figures). Disk savings on originals are more modest.

Cloud storage (S3, Swift)?
Designed for a local file system; non-local backends are detected and reported (not supported as-is).

12. Uninstallation

  1. Remove wfLoadExtension( 'VaultTecMediaOptimizer' ); and the $wgVaultTecMediaOptimizer* settings.
  2. Purge the page cache: pages revert to plain <img> (originals intact).
  3. (Optional) Delete images_webp/ (and images_avif/) to reclaim space.
  4. (Optional) Drop the tables; remove the extension folder and installed binaries.
Important. Originals are never deleted. After uninstall your media library is complete; only the regenerable WebP/AVIF versions disappear.

13. Security

13.1 External binary execution

Binaries (gifsicle, zopflipng, oxipng, vips) run via proc_open/exec with arguments passed as an array (no shell string) → no shell interpretation, no command injection. Paths come only from admin configuration.

13.2 Path-traversal protection

On-demand WebP rejects any name with .., a separator (/ or \) or a NUL byte.

13.3 Restriction to allowed types

Processing is limited to the configured MIME types and capped by …MaxFileSize.

13.4 Access rights

Special pages and sensitive actions require vaulttecmediaoptimizer-admin.

13.5 Harmlessness of generated markup

The rewrite wraps existing <img> and adds a WebP/AVIF source; original attributes are preserved and URLs encoded. No arbitrary data is injected.

Via Special:VTMOBackfill (queue), or — recommended for large wikis — the CLI (§8.6). Ensure the queue is processed (in a screen); follow progress on Special:VTMOStats.

16. Benchmarks — cost / benefit NEW

Two families. (A) a cost/benefit model of the real wiki, recomputed from explicit assumptions; (B) real measurements (PHP 8.4, libvips 8.15.1, ImageMagick 6.9.12, gifsicle 1.94, zopflipng, PHP-GD; single core). Reproducible via docs/benchmarks/model.py and tests/integration/pipeline.php.

Model assumptions (decimal units; 365 d/yr): originals 52.62 GB PNG+JPEG; traffic upper bound (cold cache) 100k views/day × 10 thumbnails; average thumbnail 55.3 KB; lossless thumbnail optimization −13.7%; WebP of thumbnail −34% (≈ −43% vs raw); original recompression −7/−16/−24% (low/median/high); WebP copies ≈ 70% of the optimized original, stored in addition.

Honest framing. Pages serve thumbnails (already small), not originals, and WebP adds disk. We separate served bandwidth (the real benefit) from per-file compression.

16.1 Served bandwidth

~55 → ~31 GB/day (−43%), ~8.7 TB/year — cold-cache upper bound.

The −43% ratio is robust; the absolute TB/year shrinks with browser/CDN caching.

16.2 Disk: WebP adds to it

Disk goes up (52.6 → ~75 GB median); the trade-off is a one-time disk cost (~+22 GB) vs a recurring bandwidth saving.

16.3 Per-file compression (measured) — ≠ bandwidth

Per-file gains (not traffic); the engine matters (GD ≈ 2.7× larger lossless); AVIF gain is quality/encoder-dependent (not always smaller).

16.4 GIF & 2nd-pass PNG (disk)

gifsicle −60 to −66% (lossless, ~20 ms); zopflipng second pass ~−12% disk but slow (~14 s).

16.5 Engine: memory, speed, throughput

libvips ~1.8× less memory (large image), ~5× less / ~40× faster (thumbnails); throughput ~245→~65 img/min by media richness (bandwidth stays ~−71/−72%).

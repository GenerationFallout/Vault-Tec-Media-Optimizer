3. Installation des dépendances

L'extension fonctionne avec un minimum : une bibliothèque d'image avec support WebP. Tout le reste est optionnel et n'apporte qu'un bénéfice ciblé.

zopflipng2ᵉ passe PNG sans perte (compression max)Non — gain disque

3.1 Bibliothèque d'image : Imagick (recommandé) ou GD

# Debian / Ubuntu
sudo apt install php-imagick        # recommandé (vraie transparence/ICC, vrai WebP lossless)
sudo apt install php-gd             # repli, souvent déjà présent
# RHEL / Alma / Rocky / Fedora
sudo dnf install php-imagick php-gd
sudo systemctl restart php-fpm apache2 2>/dev/null || true

Vérifiez le support WebP (sans lui, aucune génération possible) :

php -r 'echo extension_loaded("imagick")&&in_array("WEBP",Imagick::queryFormats())?"Imagick+WebP OK\n":"";'
php -r '$i=gd_info();echo !empty($i["WebP Support"])?"GD+WebP OK\n":"GD sans WebP\n";'
GD ≠ vrai WebP/AVIF sans perte. GD n'a pas de mode lossless réel (il approxime en qualité 100) : sur une capture d'UI à aplats, GD produit un WebP ~2,7× plus gros qu'Imagick/libvips (mesuré : 19 Ko vs 6,9 Ko, §4.4). Pour les PNG nets, préférez Imagick ou libvips.

3.2 Optimisation GIF : gifsicle

# Debian / Ubuntu
sudo apt install gifsicle
# RHEL / Alma / Rocky / Fedora (EPEL)
sudo dnf install gifsicle
gifsicle --version | head -1

Activation (off par défaut) : $wgVaultTecMediaOptimizerGifsicleEnabled = true; — niveau via …GifsicleLevel (1–3, défaut 3), chemin via …GifsicleBinary. Strictement sans perte et sûr pour l'animation : seul -O{niveau} est passé (jamais de resize / lossy / colors). Si gifsicle manque, c'est un no-op inoffensif — la génération WebP continue.

3.3 Seconde passe PNG : zopflipng (max) ou oxipng (rapide)

sudo apt install zopfli      # /usr/bin/zopflipng (Debian/Ubuntu) — compression max, LENT
cargo install oxipng         # oxipng (Rust, multi-thread, rapide) si non empaqueté
Piège open_basedir (mutualisé/Plesk). Si PHP est restreint, un binaire dans /usr/bin reste invisible côté web. Règle d'or : copiez le binaire dans l'arborescence du wiki (ex. httpdocs/bin/oxipng), chmod 755, propriétaire = utilisateur PHP, puis configurez le chemin absolu. Idem pour vips, zopflipng et gifsicle.

3.4 Moteur libvips (optionnel — voir §4 pour le gain)

# Debian/Ubuntu : sudo apt install libvips-tools   |   RHEL/Fedora : sudo dnf install vips-tools
# Alpine : apk add vips-tools                        |   macOS (dev) : brew install vips
vips --version ; vips -l | grep -i webpsave

Activation : $wgVaultTecMediaOptimizerImageEngine = 'vips'; (+ …VipsBinary si besoin). Si le binaire est inutilisable, l'extension retombe automatiquement sur Imagick/GD.

3.5 AVIF (expérimental)

L'AVIF exige un encodeur AV1 : Imagick compilé avec libheif+AV1, PHP-GD avec imageavif(), ou libvips avec heifsave+AV1. Beaucoup de paquets exposent heifsave pour le HEIC sans AV1 — l'extension le détecte et sert alors le WebP. Test réel de la capacité AV1 de vips :

vips black /tmp/p.png 16 16 && vips heifsave /tmp/p.png /tmp/p.avif --compression av1 \
  && echo "AV1 OK" || echo "AV1 indisponible"

4. Benchmarks de performance (mesures réelles & pondérées)

4.1 Méthodologie

Mesures réalisées sur la machine de test : PHP 8.4, libvips 8.15.1, ImageMagick 6.9.12, gifsicle 1.94, zopflipng, un seul cœur. Corpus synthétique varié (17 fichiers réels, ~75 Mo : photos, captures d'UI à aplats, grandes photos PNG, GIF animés). Temps = horloge murale ; mémoire = pic RSS via /usr/bin/time. Pondération : pour rester honnête, on n'affiche pas un seul chiffre mais une fourchette basse / moyenne / haute obtenue en agrégeant les mêmes mesures par catégorie selon trois profils de wiki (poids par nombre de fichiers, détaillés en §4.2) ; la bande passante est pondérée par octets (ce qui détermine réellement le trafic), le débit par fichier. Les chiffres absolus dépendent de la machine et des images ; ce sont les ordres de grandeur et ratios qui comptent. Reproduisez avec tests/integration/pipeline.php et vos propres images.

4.3 GIF sans perte (gifsicle) & 2ᵉ passe PNG

OpérationAvantAprèsGainTemps
GIF animé — gifsicle -O3 (sans perte, sur disque)——−66 %~0,02 s
PNG original — 1ʳᵉ passe (recompression sans perte)41,9 Ko32,5 Ko−22 %<0,2 s
PNG original — + 2ᵉ passe zopflipng ×1532,5 Ko28,6 Ko−12 % de plus13,7 s

gifsicle est quasi gratuit (~20 ms) et fait gagner −66 % sur les GIF, sans toucher à l'animation. À l'inverse, zopflipng est lent (≈14 s même pour un petit PNG) pour un gain disque marginal : réservez-le à une finition ponctuelle hors trafic, ou préférez oxipng.

4.4 Moteur : vitesse & mémoire (libvips vs ImageMagick)

Même bibliothèque libwebp ⇒ WebP de taille/qualité identique ; on compare donc temps et mémoire.

ScénarioMoteurPic mémoireTemps
Grande image 12 Mpx → WebPlibvips98 Mo2,2 s
ImageMagick177 Mo1,9 s
Miniature 320 px (redim. + WebP)libvips31 Mo0,03 s
ImageMagick162 Mo1,2 s

Lecture honnête. Sur une grande image, libvips utilise ~1,8× moins de mémoire (temps comparable). Sur le pipeline de miniatures — exactement la charge d'un backfill et de la génération à la volée — il est ~5× plus léger en mémoire et radicalement plus rapide (la vignette n'oblige pas à décoder toute l'image). En clair : vips vaut le coup à l'échelle, pas pour quelques fichiers isolés.

WebP lossless : qualité du moteur. Sur une capture d'UI à aplats, libvips/Imagick produisent un vrai WebP sans perte de 6,9 Ko là où GD (qualité 100, near-lossless) sort 19 Ko — soit ~2,7× plus gros. Le moteur compte autant que le format.

4.5 AVIF vs WebP (expérimental)

SourceWebP q85AVIF q50AVIF vs WebP
Photo 2000×1500201 Ko44 Ko−78 %

L'AVIF est nettement plus compact que le WebP, au prix d'un encodage plus lent. Avertissement réel mesuré : sur l'environnement de test, vips heifsave … --compression av1 a répondu Unsupported compression (build sans AV1) ⇒ l'extension serait retombée sur le WebP, tandis que PHP-GD imageavif() était, lui, disponible. C'est exactement pourquoi l'extension sonde réellement la capacité AV1 avant de produire de l'AVIF.

5. Bonnes pratiques anti-ralentissement

5.1 D'où vient le risque ?

  • File de tâches sur les requêtes web. Par défaut, MediaWiki exécute des jobs en fin de requête ($wgJobRunRate) : ce sont alors vos visiteurs qui « paient » l'encodage.
  • Génération WebP à la volée au rendu. Le premier affichage d'une page froide encode les WebP manquants des miniatures qu'elle utilise (borné par OnDemandThumbLimit).
  • 2ᵉ passe synchrone (si activée). zopflipng sur une miniature peut coûter plusieurs centaines de ms à plusieurs secondes (cf. §4.3).

5.2 Première installation (surtout gros wiki)

Option A — tout en CLI (recommandé gros wiki)Option B — par la file, maîtrisée
// LocalSettings.php
$wgVaultTecMediaOptimizerUseJobQueue = false;
Puis dans un screen : 
php maintenance/run.php \
  .../optimizeImages.php --batch=200
Hors file, sans impacter les visiteurs. Reprenable (--start), filtrable (--format=gif).		 
// LocalSettings.php — 0, pas plus !
$wgJobRunRate = 0;
Puis videz la file en SSH : 
php maintenance/run.php runJobs.php \
  --type VaultTecMediaOptimizerOptimizeImage
Jobs résiduels : purgeQueue.php.
Ne montez pas $wgJobRunRate : cela aggrave le ralentissement (plus de jobs lourds sur les requêtes visiteurs). Pour un traitement lourd, la bonne valeur est 0, combinée à un runJobs.php en SSH — ou le script CLI dédié.
  • Choisissez le moteur selon le volume. Grosse photothèque → libvips (mémoire/vitesse, §4.4).
  • Réglez OnDemandThumbLimit (défaut 5) : bas = premiers rendus plus légers ; 0 = tout par le backfill.
  • Purgez les caches À LA FIN (wiki + CDN), pas pendant.

5.3 Usage courant

  • GIF : activez gifsicle — gain franc (−66 %), coût négligeable, animation préservée.
  • 2ᵉ passe PNG : facultative et de préférence oxipng ; gardez zopflipng pour une finition hors trafic.
  • En-têtes de cache HTTP longs sur images_webp/ (et images_avif/) : levier majeur souvent oublié pour réduire réellement la bande passante.
  • Ne mélangez pas file et CLI sur le même corpus (écritures atomiques = pas de corruption, mais travail en double).
  • Droits : lancez les scripts sous l'utilisateur PHP, jamais en root.

sudo apt install zopfli      # /usr/bin/zopflipng (Debian/Ubuntu) — max compression, SLOW
cargo install oxipng         # oxipng (Rust, multi-threaded, fast) when not packaged
open_basedir trap (shared hosting/Plesk). If PHP is restricted, a binary in /usr/bin stays invisible to the web side. Golden rule: copy the binary inside the wiki tree (e.g. httpdocs/bin/oxipng), chmod 755, owner = PHP user, then configure the absolute path. Same for vips, zopflipng and gifsicle.

4. Performance benchmarks (measured & weighted)

4.1 Methodology

Measured on the test machine: PHP 8.4, libvips 8.15.1, ImageMagick 6.9.12, gifsicle 1.94, zopflipng, single core. A varied synthetic corpus (17 real files, ~75 MB: photos, flat UI captures, large PNG photos, animated GIFs). Time = wall clock; memory = peak RSS via /usr/bin/time. Weighting: to stay honest, we show not a single number but a low / medium / high range, obtained by aggregating the same per-category measurements under three wiki profiles (weights by file count, detailed in §4.2); bandwidth is weighted by bytes (what actually drives traffic), throughput by file. Absolute numbers depend on machine and images; the orders of magnitude and ratios are what matter. Reproduce with tests/integration/pipeline.php and your own images.

4.4 Engine: speed & memory (libvips vs ImageMagick)

Same libwebp library ⇒ identical WebP size/quality; we therefore compare time and memory.

ScenarioEnginePeak memoryTime

Honest reading. On a large image, libvips uses ~1.8× less memory (comparable time). On the thumbnail pipeline — exactly the load of a backfill and on-the-fly generation — it is ~5× lighter on memory and dramatically faster (a thumbnail need not decode the whole image). In short: vips pays off at scale, not for a handful of files.

Lossless WebP: the engine matters. On a flat UI capture, libvips/Imagick produce a true lossless WebP of 6.9 KB where GD (quality 100, near-lossless) emits 19 KB — ~2.7× larger. The engine matters as much as the format.

5. Best practices to avoid slowdowns

5.1 Where does the risk come from?

  • Job queue on web requests. By default MediaWiki runs jobs at the end of requests ($wgJobRunRate): your visitors then pay for the encoding.
  • On-the-fly WebP generation at render. The first view of a cold page encodes the missing WebP files for the thumbnails it uses (bounded by OnDemandThumbLimit).
  • Synchronous 2nd pass (if enabled). zopflipng on a thumbnail can cost hundreds of ms to several seconds (see §4.3).

5.2 First install (especially large wikis)

Option A — all CLI (recommended for large wikis)Option B — via the queue, controlled
// LocalSettings.php
$wgVaultTecMediaOptimizerUseJobQueue = false;
Then in a screen: 
php maintenance/run.php \
  .../optimizeImages.php --batch=200
Off-queue, no visitor impact. Resumable (--start), filterable (--format=gif).		 
// LocalSettings.php — 0, no more!
$wgJobRunRate = 0;
Then drain the queue over SSH: 
php maintenance/run.php runJobs.php \
  --type VaultTecMediaOptimizerOptimizeImage
Leftover jobs: purgeQueue.php.
Do not raise $wgJobRunRate: it worsens the slowdown (more heavy jobs on visitor requests). For heavy processing the right value is 0, combined with runJobs.php over SSH — or the dedicated CLI script.
  • Pick the engine by volume. Large media library → libvips (memory/speed, §4.4).
  • Tune OnDemandThumbLimit (default 5): low = lighter first renders; 0 = everything via the backfill.
  • Purge caches AT THE END (wiki + CDN), not during.

5.3 Everyday use

  • GIF: enable gifsicle — clear gain (−66%), negligible cost, animation preserved.
  • 2nd-pass PNG: optional and preferably oxipng; keep zopflipng for an off-traffic finishing pass.
  • Long HTTP cache headers on images_webp/ (and images_avif/): a major, often forgotten lever to actually cut bandwidth.
  • Don't mix queue and CLI on the same corpus (atomic writes = no corruption, but duplicated work).
  • Permissions: run scripts as the PHP user, never as root.

1. À propos de ce document

Ce document complète le guide d'installation et d'administration v1.4.1. Il ne le répète pas : il se concentre sur trois sujets demandés et peu (ou pas) couverts ailleurs — l'installation des dépendances, des benchmarks de performance mesurés, et les bonnes pratiques anti-ralentissement. Pour la configuration générale, les pages spéciales, le dépannage et le tutoriel pas-à-pas, reportez-vous au guide v1.4.1 ; pour les nouveaux paramètres (moteur d'image, file de tâches), au fichier docs/NEW_FEATURES.md.

Sans doublon. Les commandes de configuration ne sont rappelées ici que lorsqu'elles sont indispensables à la compréhension d'une dépendance ou d'une bonne pratique. Le détail des paramètres vit dans le guide et dans NEW_FEATURES.md.

2. Installation des dépendances

L'extension fonctionne avec un minimum : une bibliothèque d'image avec support WebP. Les autres dépendances sont optionnelles et n'apportent qu'un bénéfice ciblé.

DépendanceRôleObligatoire ?
Imagick ou GD (avec WebP)1ʳᵉ passe + encodage WebPOui (l'une des deux)
libvips (vips)Moteur alternatif rapide/léger (§3)Non — opt-in
zopflipng2ᵉ passe PNG sans perte (compression max)Non — gain disque
oxipng2ᵉ passe PNG sans perte (rapide)Non — gain disque
libheif+AV1 / imageavif()AVIF expérimentalNon — expérimental

2.1 Bibliothèque d'image : Imagick (recommandé) ou GD

uk# Debian / Ubuntu
sudo apt install php-imagick        # recommandé (meilleure transparence/ICC)
sudo apt install php-gd             # repli, souvent déjà présent
# RHEL / Alma / Rocky / Fedora
sudo dnf install php-imagick php-gd
sudo systemctl restart php-fpm apache2 2>/dev/null || true

Vérifiez le support WebP de la bibliothèque (sans lui, pas de génération possible) :

php -r 'echo extension_loaded("imagick")&&in_array("WEBP",Imagick::queryFormats())?"Imagick+WebP OK\n":"";'
php -r '$i=gd_info();echo !empty($i["WebP Support"])?"GD+WebP OK\n":"GD sans WebP\n";'

La page Spécial:VaultTec_État affiche clairement la bibliothèque active et son support WebP.

2.2 Moteur libvips (optionnel — voir §3 pour le gain)

C'est le binaire en ligne de commande vips qui est utilisé (aucune extension PHP requise).

# Debian / Ubuntu
sudo apt install libvips-tools
# RHEL / Alma / Rocky / Fedora (EPEL)
sudo dnf install vips-tools
# Alpine (Docker)
apk add vips-tools
# macOS (dev)
brew install vips

Vérification :

vips --version                 # ex. vips-8.15.1
vips -l | grep -i webpsave     # le sauveur WebP doit être listé

Activation (détails dans NEW_FEATURES.md) : $wgVaultTecMediaOptimizerImageEngine = 'vips'; et, si besoin, le chemin absolu via …VipsBinary. Si le binaire est inutilisable, l'extension retombe automatiquement sur Imagick/GD.

2.3 Seconde passe PNG : zopflipng

sudo apt install zopfli      # fournit /usr/bin/zopflipng (Debian/Ubuntu)
sudo dnf install zopfli      # RHEL/Fedora (EPEL)
zopflipng --version 2>/dev/null; command -v zopflipng

zopflipng = compression maximale mais lent. Réservez-le à la finition (voir §4).

2.4 Seconde passe PNG : oxipng (recommandé pour le volume)

oxipng (Rust, multi-thread, rapide) n'est pas toujours en paquet. Deux voies :

# Via Rust (compilation sur la machine — évite les soucis de glibc)
cargo install oxipng
# Ou binaire précompilé (attention à « GLIBC_2.xx not found » : préférez compiler)
Piège open_basedir (mutualisé/Plesk). Si PHP est restreint, un binaire dans /usr/bin reste invisible côté web. Règle d'or : copiez le binaire dans l'arborescence du wiki (ex. httpdocs/bin/oxipng), chmod 755, propriétaire = utilisateur PHP, puis configurez le chemin absolu. Idem pour vips et zopflipng.

2.5 AVIF (expérimental)

L'AVIF exige un encodeur AV1, via l'un de : Imagick compilé avec libheif+AV1, PHP-GD avec imageavif(), ou libvips avec heifsave+AV1. Beaucoup de paquets exposent heifsave pour le HEIC sans AV1 — l'extension le détecte et sert alors le WebP. Pour tester réellement la capacité AV1 de vips :

vips black /tmp/p.png 16 16 && vips heifsave /tmp/p.png /tmp/p.avif --compression av1 \
  && echo "AV1 OK" || echo "AV1 indisponible"

3. Benchmarks de performance (mesures réelles)

3.1 Méthodologie

Mesures réalisées sur cette machine de test avec libvips 8.15.1, ImageMagick 6, cwebp et zopflipng 1.0.3. Images synthétiques représentatives : une photo « plasma » (photographique, bruitée) et une capture documentaire (aplats + texte). Mémoire = pic RSS via /usr/bin/time -v ; temps = horloge murale. Les chiffres absolus dépendent de la machine et des images ; ce sont les ordres de grandeur et ratios qui importent.

3.2 Compression / espace

SourceOpérationAvantAprèsGain
Photo JPEG (q90)→ WebP q85613 Ko250 Ko−59 %
Photo PNG→ WebP lossless10,1 Mo3,2 Mo−68 %
Photo PNG→ WebP q85 (avec perte)10,1 Mo254 Ko−97 %
Capture PNG→ WebP lossless52,5 Ko9,3 Ko−82 %
Capture PNG (original)1ʳᵉ passe (recompression sans perte)52,5 Ko49,4 Ko−6 %
Capture PNG (original)+ 2ᵉ passe zopflipng49,4 Ko41,2 Ko−17 % de plus

Lecture. Le gros bénéfice visiteur vient du WebP servi (−59 % à −97 % selon l'image). La recompression sans perte de l'original (1ʳᵉ + 2ᵉ passe) ne gagne que quelques % à ~20 % d'espace disque — utile seulement si le stockage est une contrainte. C'est conforme à la conception : le WebP est le vrai levier de bande passante, la 2ᵉ passe un bonus disque.

3.3 Vitesse & mémoire selon le moteur

Même encodage WebP, moteurs différents. Le WebP produit est de taille/qualité équivalente entre vips et cwebp (même bibliothèque libwebp) ; on compare donc surtout temps et mémoire.

ScénarioMoteurPic mémoireTemps
Grande image 12 Mpx → WebPlibvips102 Mo2,3 s
ImageMagick174 Mo2,5 s
Miniature 320 px (redim. + WebP)libvips61 Mo0,7 s
ImageMagick163 Mo0,9 s
Petite image 1,9 Mpx → WebPlibvips ≈ ImageMagick~40–46 Mo~0,4 s

Lecture honnête. L'avantage de libvips est net sur les grandes images (~1,7× moins de mémoire) et surtout les pipelines de miniatures (~2,7× moins, et plus rapide) — exactement la charge d'un gros backfill et de la génération à la volée. Sur une petite image isolée, la différence est négligeable (l'empreinte de base de libvips peut même la rendre légèrement supérieure). En clair : vips vaut le coup à l'échelle, pas pour quelques fichiers.

À retenir. vips ne réduit pas le poids des images servies (même libwebp que GD/Imagick) : il fait gagner du temps de traitement et de la mémoire serveur. AVIF non mesuré ici (pas d'encodeur AV1 dans l'environnement de test).

4. Bonnes pratiques anti-ralentissement

4.1 D'où vient le risque ?

  • File de tâches sur les requêtes web. Par défaut MediaWiki exécute des jobs à la fin des requêtes ($wgJobRunRate). Or chaque job d'optimisation lance un encodage : ce sont alors vos visiteurs qui « paient » le traitement, et le wiki paraît lent.
  • Génération WebP à la volée au rendu. Le premier affichage d'une page « froide » encode les WebP manquants des miniatures qu'elle utilise (borné par OnDemandThumbLimit).
  • 2ᵉ passe synchrone (si activée). zopflipng sur une miniature pendant le rendu peut coûter plusieurs centaines de ms.

4.2 Première installation (surtout gros wiki)

  1. Ne déclenchez pas le backfill par la file pendant les heures de trafic. Deux options propres :
Option A — tout en CLI (recommandé gros wiki)Option B — par la file, maîtrisée
// LocalSettings.php
$wgVaultTecMediaOptimizerUseJobQueue = false;
Puis, dans un screen : 
php maintenance/run.php \
  .../optimizeImages.php --batch=200
Traite les originaux hors file, sans impacter les visiteurs. Reprenable (--start). 
// LocalSettings.php — 0, pas plus !
$wgJobRunRate = 0;
Puis videz la file vous-même en SSH : 
php maintenance/run.php runJobs.php \
  --type VaultTecMediaOptimizerOptimizeImage
Si des jobs traînent d'un essai précédent : purgeQueue.php.
Ne montez pas $wgJobRunRate (contrairement à certains messages génériques de MediaWiki) : cela aggrave le ralentissement en exécutant plus de jobs lourds sur les requêtes visiteurs. Pour un traitement lourd, la bonne valeur est 0, combinée à un runJobs.php en SSH — ou carrément le script CLI dédié.
  1. Lancez les gros traitements dans screen/tmux pour survivre à une déconnexion.
  2. Choisissez le moteur selon le volume. Grosse photothèque → activez libvips (mémoire/vitesse, §3).
  3. Réglez OnDemandThumbLimit (défaut 5) : valeur basse = premiers rendus plus légers ; 0 = aucune génération à la volée (tout par le backfill).
  4. Purgez les caches À LA FIN (wiki + CDN), pas pendant — purger en cours re-met en cache d'anciennes versions.

4.3 Usage courant

  • 2ᵉ passe PNG : facultative, et de préférence oxipng. Elle ne profite qu'au disque. Si vous l'activez, préférez oxipng (rapide) ; gardez zopflipng pour une finition ponctuelle hors trafic.
  • En-têtes de cache HTTP longs sur images_webp/ (et images_avif/) : levier majeur et souvent oublié pour réduire réellement la bande passante côté navigateur/CDN.
  • Ne mélangez pas file et CLI sur le même corpus en même temps (utilisez --purge-queue).
  • Concurrence. Évitez de lancer un script CLI pendant que la file traite le même stock : les écritures sont atomiques (pas de corruption), mais vous feriez du travail en double.
  • Droits. Lancez les scripts sous l'utilisateur de PHP, jamais en root (sinon fichiers non réécrasables ensuite).
